AI in 2027 // Developer edition

Ten habits for working with AI.

Use it on real work. Ask for something you can inspect.

Code, presentations and posts all need someone who can judge the result.

Chuck Blake // AI in 2027 // Developer edition

Speaker notes

Ask what people have tried and where the review got expensive. These are working habits, not a forecast of what every tool will do in 2027. The examples are illustrative prompts and workflows, not reports of completed projects. Start small enough that you can check the work yourself.

Tip 1 / 10

Put AI between you and the work.

Before you start, ask: "How could AI help with this?"

  • Ask for an explanation of unfamiliar code, or a review of a draft.
  • Choose a small task whose result you can judge.
  • Do it yourself when the setup or review would cost more than the help.

Considering AI does not mean granting access. Keep private data and secrets out of the experiment.

Speaker notes

Make this a pause before starting, not a requirement to use AI for every task. Read-only work is a reasonable first step. Use approved tools and test data. If the task needs sensitive access, resolve that separately rather than putting permission into a vague prompt.

Tip 2 / 10

Define what finished looks like.

Illustrative brief for a small bug fix:

"Fix the empty-state crash. Add a regression test. Return a diff and the check results. Leave the API and dependencies alone."

Name the output, the checks and what must stay unchanged. Ask about missing decisions before work starts.

Speaker notes

A short brief can be enough. Agree how you will judge the change before the agent writes it. For a presentation, replace the regression test with audience, outcome, source checks and a preview. Set a checkpoint if the task turns out to be larger than expected.

Tip 3 / 10

Use a tool that can work with the project.

Check the fit

Can your approved tool read the relevant files, propose changes and run the checks this task needs? Verify its actual setup.

Keep access narrow

Use a local copy or review branch. Allow only the files and commands the task needs; approve broader access separately.

For a web artifact, ask for an editable file and a local preview you can open.

Speaker notes

This is a selection checklist, not a claim that every AI product has these capabilities. Check documentation, installed version, tool permissions and the working directory. A prompt describes the boundary; permissions enforce it. Avoid choosing a product on an unverified demo or a promise of superiority.

Tip 4 / 10

Ask it to trace the code before changing it.

"Trace this request from the entry point to storage. Point to the files and tests. Mark anything you cannot follow. Do not edit yet."

Check the path against the code. Then agree where the change belongs.

A plausible walkthrough can still describe a path the application never takes.

Speaker notes

Ask for file paths and relevant symbols, not hidden reasoning. Open the references and look for missing branches, permissions and failure paths. If the tool cannot see a dependency or runtime setting, it should say so. For a post or deck, first trace the source material and the site's publishing conventions.

Tip 5 / 10

Ask for work you can open after the chat.

Artifacts are durable outputs you can inspect, edit and hand off.

Documents, diagrams, prototypes, diffs, sample files, presentations and posts.

The work

Ask for the editable file, its location and a way to open or preview it.

The handoff

Ask for sources, decisions, checks that ran and anything still unresolved.

Speaker notes

Artifact means a durable output, not one vendor's interface. A diff may be the right artifact for code; a source file and preview may be right for a presentation. Open the file rather than relying on a screenshot or summary. The handoff should make sense to someone who did not read the chat.

Tip 6 / 10

Revise the part that needs work.

Illustrative revision request:

"On the artifacts slide, define the term in plain English and add presentations and posts. Keep the other slides and navigation unchanged."

Name the file, section or behavior. Review the diff for changes outside that scope.

Speaker notes

Keep the artifact open beside the conversation. A specific correction is easier to check than asking for a better version of everything. If the request reveals a larger problem, agree a new scope before rewriting. Run the relevant checks again on the revised artifact, not only the first draft.

Tip 7 / 10

Check the result with evidence.

For code

Inspect the diff. Run the relevant tests and try the behavior, including a failure case.

For a presentation or post

Open the sources and links. Read the actual draft. Check the rendered layout and any navigation.

Ask what actually ran, what passed and what nobody checked.

A second agent can help review. Agreement between agents is not proof.

Speaker notes

Request actual command output, file references or browser receipts where appropriate. A green test can check the wrong behavior, so make an independent check against the original brief. Mark blocked checks as not run. Screenshots can support a layout check but do not prove a source says what the draft claims.

Worked example // Communication artifact

Build a presentation or post for chuckblake.com.

Set the brief

Name the audience and what they should understand or do. Point to the source material and site conventions.

Make the first artifact

Ask for editable source and a local preview. Open it, inspect it and request targeted revisions.

Check the draft

Verify sources, links and layout. For a deck, test navigation and print. Have a person review the final version.

Publish later

Publish only after approval. Then check the live page and keep an owner for corrections.

Illustrative workflow. A local preview is not a published page.

Speaker notes

This is a supporting example, not an eleventh tip. For a deck, keep speaker notes, deep links and the PDF in scope. For a post, check the headline, quotations and site rendering. The agent should stop at the local preview unless publishing is explicitly authorized. After a later release, open the live URL and repeat the checks that depend on deployment.

Tip 8 / 10

Save the procedures worth repeating.

Turn a useful workflow into instructions you can read and change.

  • Write when to use it, the steps, required access and when to stop.
  • Include the checks that tell you whether it worked.
  • Read and adapt third-party instructions before letting them use tools.

Optional examples: Matt Pocock's skills for clarifying a plan or test-driven work. Source [23]

Speaker notes

A saved procedure can be a Markdown file or checklist. You do not need a collection of skills to start. Pocock's repository is an optional source to read and adapt, not an endorsement of every instruction or permission it requests. Check the current instructions against your project and keep secrets out of saved examples.

Tip 9 / 10

Keep learning from the work.

  • Record the task, the result and what you had to correct.
  • Count the time spent briefing, inspecting, revising and checking.
  • Use failures to change the next attempt. Share the useful checks with your team.
  • Revisit a workflow when the tool or project changes. Stop using it if the cost no longer makes sense.

Judge quality and total effort. Generated lines and busy agents do not tell you whether the work helped.

Speaker notes

Keep the record small enough that you will use it. Review effort is part of the cost, even when the first draft arrives quickly. Maintain your own debugging and domain knowledge so you can challenge the result. Changing a tool or model is a reason to rerun the checks, not assume the old result still holds.

Tip 10 / 10

Own the release.

You decide what ships. You remain responsible for what happens afterward.

Before release

Review the final code, presentation or post. Resolve blocked checks and get the required approval.

After release

Check the live result. Fix bugs, broken links or incorrect claims. Know who can roll back or correct it.

Name the owner before publishing. An AI-written change still needs someone to answer for it.

Speaker notes

Keep accountability with a person and the organization. Code can break after a release; a deck can publish an unsupported claim; a post can misquote a source. Decide who handles those problems. A local pass is not a live-site check. Publishing, production access and rollback are separate permissions from making a draft.

Closing exercise

Try it on one real task.

Choose a development task or a communication artifact you already need.

  • Write what finished looks like and what you will inspect.
  • Make an editable first artifact. Open it and request one specific revision.
  • Compare the result with the brief. Was the quality good enough, and was the total review effort worth it?
